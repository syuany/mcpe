## 一、 容器化交付与全栈编排体系 (Docker & Deployment)

### 1.1 Docker 多阶段构建 (Multi-Stage Build)
为了使生产镜像体积最小化并杜绝编译工具链引入的安全隐患，MCPE 采用标准的 Docker 多阶段镜像构建流水线：

```dockerfile
# 阶段一：构建环境 (Builder)
FROM debian:bookworm-slim AS builder
RUN apt-get update && apt-get install -y \
    build-essential cmake ninja-build clang-16 libasio-dev \
    && rm -rf /var/lib/apt/lists/*

WORKDIR /workspace
COPY . .
RUN cmake -B build -G Ninja \
    -DCMAKE_BUILD_TYPE=Release \
    -DCMAKE_CXX_COMPILER=clang++-16 \
    -DENABLE_LTO=ON \
    && cmake --build build --target mcpe_server -j$(nproc)

# 阶段二：生产运行极简镜像 (Runtime)
FROM debian:bookworm-slim AS runtime
RUN apt-get update && apt-get install -y ca-certificates libstdc++6 \
    && rm -rf /var/lib/apt/lists/*

WORKDIR /app
COPY --from=builder /workspace/build/mcpe_server /app/mcpe_server
COPY config/ /app/config/

EXPOSE 25565
ENTRYPOINT ["/app/mcpe_server"]
```

### 1.2 Docker Compose 全栈编排方案
在单机及边缘节点上，通过 Docker Compose 一键拉起完整游戏微服务矩阵：


## 二、 配置热更新与优雅启停 (Hot-Reload & Graceful Shutdown)

### 2.1 基于 SIGHUP 信号的无停机配置热重载
在生产环境下，运营人员常常需要动态调整 MOTD、增加最大在线人数、修改观察视距或封禁名单。MCPE 捕获 Linux 的 `SIGHUP` 信号实现零停机热更：

```cpp
void setupSignalHandlers(asio::io_context& ioc, ConfigManager& cfg) {
    auto signals = std::make_shared<asio::signal_set>(ioc, SIGHUP, SIGINT, SIGTERM);
    signals->async_wait([&cfg, signals, &ioc](const boost::system::error_code& error, int signal_number) {
        if (!error) {
            if (signal_number == SIGHUP) {
                cfg.reloadConfigFile(); // 重新加载 server.properties / JSON
                // 仅更新原子变量或线程安全状态，绝不重启网络端口
            } else if (signal_number == SIGINT || signal_number == SIGTERM) {
                gracefulShutdown(ioc);
            }
        }
    });
}
```

### 2.2 优雅退出 (Graceful Shutdown) 标准 SOP
当接收到 `SIGINT` 或 `SIGTERM` 退出信号时，严禁粗暴 `kill -9`，必须严格执行以下排空步骤：
1. **停止接入新连接**：调用 `TcpServer::stop()`，关闭监听 Socket，不再接受任何新的握手。
2. **下发优雅断开通知**：向所有在线玩家的会话广播 `Disconnect (Play 0x1A)`，告知 `"Server is shutting down for maintenance"`。
3. **安全刷盘 Checkpoint**：强制触发世界区块与玩家未提交数据的写回（MySQL & Anvil），确保零数据丢失。
4. **排空在途异步发送队列**：等待所有会话的 Strand 发送缓冲区写入 Socket 完成（最多等待 3 秒）。
5. **正常关闭 `io_context` 并退出进程**，退出码为 0。

## 三、 全链路可观测性与 Prometheus 监控大盘 (Metrics)

MCPE 内置轻量级 HTTP Metrics 收集器，以标准 Prometheus 文本格式向 `:9100/metrics` 输出监控指标。

### 3.1 核心度量指标规范 (Metrics Dictionary)

| 指标名称 | 类型 | 标签 (Labels) | 业务含义与监控阈值 |
| :--- | :---: | :--- | :--- |
| **`mcpe_server_tps`** | `Gauge` | `dimension="overworld"` | **当前物理帧率 (TPS)**。基准值为 20.0。若持续 30 秒 $< 18.0$，触发 P1 级性能报警 |
| **`mcpe_tick_duration_ms`** | `Histogram` | `le="10,25,50,100,250"` | **单 Tick 执行耗时**。正常应在 $1\sim 5\text{ms}$ 内完成；若 P99 超过 $50\text{ms}$ 说明发生卡顿 |
| **`mcpe_online_players`** | `Gauge` | `state="playing"` | **实时在线玩家数**。用于容量规划与动态缩扩容 |
| **`mcpe_active_sessions`** | `Gauge` | `type="tcp"` | **TCP 底层活动连接数**（含探测中、登录中连接） |
| **`mcpe_chunks_loaded`** | `Gauge` | `dimension="overworld"` | **当前内存驻留 Chunk 总数**。用于监控 LRU 淘汰健康度 |
| **`mcpe_packet_rate_total`**| `Counter` | `direction="in/out"` | **网络数据包吞吐率 (Packets/s)**。监控网络突发峰值 |
| **`mcpe_send_queue_depth`** | `Histogram` | `session_id` | **写队列背压深度**。若队列长期堆积，说明客户端网络恶劣或发生阻塞 |

* **Panel 1: 核心健康度总览**：实时 TPS 仪表盘（绿: 19.5~20, 黄: 17~19.5, 红: <17） + Tick 耗时趋势图。

## 四、 高并发压测方案与性能调优体系 (Benchmarking)

### 4.1 Headless Bot 千人并发压测工具
* **工具实现**：开发轻量级无头客户端（Headless Client Bot），单进程可并发生成数百个虚拟玩家：
  1. 批量建立 TCP 连接至 MCPE 端口 `25565`。
  2. 模拟真实协议状态机：发送 `Handshake (0x00)` -> `Login Start (0x00)` -> 接收 `Login Success` -> 响应 `Teleport Confirm`。
  3. 进服后以 20Hz 频率持续向服务端发送布朗运动（Brownian Motion）随机位移包与朝向包。

```
[压测梯级推进规划]
  Step 1: 100 并发 Bot (基准功能验证与单机初测)
  Step 2: 500 并发 Bot (中度并发负载，检验 AOI 九宫格性能)
  Step 3: 1000 并发 Bot (高并发达标测试，检验 20 TPS 稳定性)
  Step 4: 2000 并发 Bot (极限浸泡压测，寻找系统瓦解临界点)
```

### 4.2 Linux `perf` 性能剖析与火焰图 (FlameGraph) 分析
在 1000 Bot 高负载运行期间，使用 Linux `perf` 进行无侵入式 CPU 采样：

```bash
# 1. 采集 60 秒 CPU 堆栈调用 (频率 99Hz，带调用栈)
sudo perf record -F 99 -p $(pidof mcpe_server) -g -- sleep 60

# 2. 解析堆栈并生成折叠格式
sudo perf script > out.perf

# 3. 渲染生成交互式 SVG 火焰图
stackcollapse-perf.pl out.perf > out.folded
flamegraph.pl out.folded > mcpe_flamegraph.svg
```

* **常见性能瓶颈与调优策略**：
  * **VarInt 解码频繁调用**：对单字节常用数字（0~127）进行快速分支预测内联（Fast-Path 优化）。
  * **JSON 字符串拼接开销**：在 MOTD 响应中预先静态化 JSON 模板，避免每次探测都动态构造 AST 树。
  * **小内存分配锁竞争**：使用定长块内存池或启用 `jemalloc` / `tcmalloc` 代替 glibc 默认 `malloc`。

### 4.3 自动化内存与竞态净化体系 (Sanitizers)
在 CI/CD 流水线中，为测试编译启用 Sanitizer 强化检测：
* **AddressSanitizer (ASan)**：`-fsanitize=address`，捕获任何内存越界访问、Use-After-Free 和内存泄漏。
* **ThreadSanitizer (TSan)**：`-fsanitize=thread`，检测多线程环境下的潜在数据竞争与锁倒序。
* **UndefinedBehaviorSanitizer (UBSan)**：`-fsanitize=undefined`，捕捉有符号整型溢出、空指针解引用等未定义行为。

## 一、 世界与区块存储架构 (World & Chunk Storage)

### 1.1 Minecraft Anvil / Region 磁盘存储规范
Minecraft 采用分层分区的 **Region 文件系统（`.mca` 格式）**，有效避免了海量单个小文件读写导致的操作系统 inode 耗尽与碎片化：
* **区域划分**：每个 Region 文件对应世界中 $32 \times 32 = 1024$ 个 Chunk（区块列），空间覆盖 $512 \times 512$ 个方块。文件名格式为 `r.x.z.mca`（例如 `r.0.0.mca` 代表覆盖方块坐标 $X: [0, 511], Z: [0, 511]$ 的区域）。

```
+─────────────────────────────────────────────────────────────────────────────────+
|                  Region Header (8192 Bytes / 2 扇区)                            |
+───────────────────────────────────────+─────────────────────────────────────────+
|      Chunk 偏移扇区定位表 (4096 字节)    |        Chunk 修改时间戳表 (4096 字节)   |
|   1024 个 Chunk 条目 (每个 4 字节)    |      1024 个 Chunk 条目 (每个 4 字节)   |
+───────────────────────────────────────+─────────────────────────────────────────+
|                              Sector Data Blocks                                 |
+─────────────────────────────────────────────────────────────────────────────────+
| Sector 2: [4 字节长度] [1 字节压缩=2] [Zlib 压缩的 NBT 区块数据...]              |
| Sector N: ...                                                                   |
+─────────────────────────────────────────────────────────────────────────────────+
```

1. **Chunk 定位表项（4 字节）**：
   - 前 3 字节（24 位）：扇区偏移号（Sector Offset，每个扇区 4096 字节）。
   - 第 4 字节（8 位）：当前 Chunk 占用的扇区计数值（Sector Count）。
   - 若偏移为 0，表示该 Chunk 尚未生成或未写入。
2. **数据压缩封装**：
   - 扇区起始处包含 4 字节大端整数记录压缩后的数据净长度，随后 1 字节标识压缩算法（`2 = Zlib/DEFLATE`）。解压后为标准的树状 NBT（Named Binary Tag）复合数据结构。

### 1.2 内存紧凑区块模型 (In-Memory Chunk Section)
在内存中，全服如果常驻成千上万个 Chunk，简单用原生数组表示将耗费数 GB 内存。MCPE 采用与官方一致的 **16x16x16 ChunkSection + Palette（调色板）紧凑模型**：

```
+─────────────────────────────────────────────────────────────────────────────────+
|                            ChunkColumn (X, Z)                                   |
+─────────────────────────────────────────────────────────────────────────────────+
|  Sections[16]: [Section 0 (Y:0~15)] [Section 1 (Y:16~31)] ... [Section 15]      |
|  HeightMap: 256 个短整型                                                        |
|  Biomes: 256 字节生物群系标识                                                   |
+─────────────────────────────────────────────────────────────────────────────────+

                    ChunkSection (16x16x16 = 4096 Blocks)
┌─────────────────────────────────────────────────────────────────────────────────┐
│ BitsPerBlock (4 ~ 8 bits)  │  Block Palette (局部调色板数组)                    │
├────────────────────────────┼────────────────────────────────────────────────────┤
│ 4 bits (至多 16 种方块)    │ [0: Air, 1: Stone, 2: Grass, 3: Dirt]              │
├────────────────────────────┴────────────────────────────────────────────────────┤
│ Packed Data Array: 64 位整数数组 (通过位偏移连续紧凑打包 4096 个调色板索引)    │
└─────────────────────────────────────────────────────────────────────────────────┘
```

* **空间节约对比**：
  * 若直接使用 16 位整型存储 4096 个方块：$4096 \times 2 = 8192\text{ Bytes}$。
  * 采用 4-bit 局部调色板打包存储：$4096 \times 4\text{ bits} = 2048\text{ Bytes}$（节约 **75% 内存**）。
  * 仅当单个 Section 内方块种类超过阈值（如 $> 8$ 种）时，退化为全局直接映射（13-bit Direct ID）。

### 1.3 异步区块 I/O 与 LRU 热点缓存
* **视距动态加卸载**：玩家在世界移动时，以玩家所在 Chunk 为中心，维护一个半径为 $R$（View Distance，默认 8）的观察视距窗口。
* **淘汰机制**：ChunkManager 内部维护基于双向链表与哈希表的 **LRU 缓存队列**。当一个 Chunk 脱离所有在线玩家的观察范围超过 60 秒时，将其标记为冷数据并触发异步安全刷盘写回，随后从内存中释放，彻底避免内存持续膨胀。

## 二、 EnderVault 分布式游戏数据中心 (Go + gRPC)

### 2.1 架构定位与 Monorepo 协同
MCPE 空间网关与世界物理引擎专注 20 TPS 物理帧率，绝对不执行阻塞式数据库读写。所有玩家账户鉴权、持久化背包数据、跨服末影箱及虚拟资产统一交由伴生微服务 **EnderVault**（位于 Monorepo 的 `services/endervault/` 目录下）托管。

```
[MCPE C++ 网关节点]
       │
       │ (High-Performance gRPC over Protobuf v3)
       ▼
[EnderVault Go 微服务] 
  ├── 1. 鉴权与会话治理 (JWT / Offline UUID 校验)
  ├── 2. 玩家资产与末影箱管理 (Inventory / Ender Chest)
  ├── 3. 分布式并发控制 (Redis 分布式锁)
  └── 4. 多级缓存管理与异步入库 (Cache-Aside + Checkpoint)
```

### 2.2 跨语言共享通信契约 (`proto/endervault.proto`)
C++ 与 Go 共享根目录下的 Protocol Buffers 契约定义：

```protobuf
syntax = "proto3";

package mcpe.endervault;
option go_package = "mcpe/services/endervault/pb";

// 道具槽位数据结构
message ItemSlot {
    int32 slot_index = 1;
    int32 item_id = 2;
    int32 count = 3;
    int32 damage = 4;
    bytes nbt_data = 5;
}

// 玩家数据总览请求与响应
message GetProfileRequest {
    string player_uuid = 1;
    string username = 2;
}

message GetProfileResponse {
    string player_uuid = 1;
    string username = 2;
    int64 coins = 3;
    int32 level = 4;
    repeated ItemSlot inventory = 5;
    repeated ItemSlot ender_chest = 6;
}

// 资产存取与交易契约 (含幂等性防重标识)
message UpdateInventoryRequest {
    string player_uuid = 1;
    string transaction_id = 2; // 唯一幂等流水号
    repeated ItemSlot items = 3;
}

message UpdateInventoryResponse {
    bool success = 1;
    string message = 2;
}

service EnderVaultService {
    rpc GetPlayerProfile(GetProfileRequest) returns (GetProfileResponse);
    rpc SavePlayerInventory(UpdateInventoryRequest) returns (UpdateInventoryResponse);
}
```

## 三、 多级缓存与关系数据库设计 (Redis + MySQL)

### 3.1 多级存储层次划分

```
[Level 1] C++ 进程内本地只读缓存 (std::unordered_map，保存当前在线玩家高频属性)
   │ (Cache Miss)
   ▼
[Level 2] Redis 7.0 分布式内存缓存 (微秒级响应，承载玩家 Session、背包、分布式互斥锁)
   │ (Cache Miss)
   ▼
[Level 3] MySQL 8.0 规范化持久层 (ACID 事务，冷数据持久化与财务/资产审计流水)
```

### 3.2 Redis 键空间与数据结构设计

| 键名规范 (Key Pattern) | 数据结构 | TTL 策略 | 业务用途与说明 |
| :--- | :---: | :---: | :--- |
| `mcpe:player:session:{uuid}` | `String` | 30 分钟 (心跳续期) | 记录玩家当前所在网关节点 ID、Token 及在线状态 |
| `mcpe:player:profile:{uuid}` | `Hash` | 2 小时 | 存储玩家等级、金币、最后登录时间等基本画像 |
| `mcpe:player:inventory:{uuid}`| `String` (Protobuf) | 2 小时 | 序列化后的玩家背包 36 格及盔甲槽物品数据 |
| `mcpe:player:enderchest:{uuid}`| `String` (Protobuf)| 2 小时 | 跨维度/跨服共享末影箱 27 格数据 |
| `mcpe:lock:trade:{uuid}` | `String` | 5 秒 (Redlock) | 交易/背包结算分布式互斥锁，防止并发刷道具 |
| `mcpe:rank:coins` | `ZSet` | 永久 | 全服财富排行榜（Score: 金币数, Member: UUID） |

### 3.3 MySQL 规范化关系表结构设计

```sql
-- 1. 玩家主账户表
CREATE TABLE `users` (
    `id` BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '自增主键',
    `uuid` CHAR(36) NOT NULL COMMENT '玩家128位UUID (规范格式带连字符)',
    `username` VARCHAR(16) NOT NULL COMMENT '玩家登录用户名',
    `created_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    `updated_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_uuid` (`uuid`),
    KEY `idx_username` (`username`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='玩家账号主表';

-- 2. 玩家资产与背包持久化表
CREATE TABLE `player_inventories` (
    `id` BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    `player_uuid` CHAR(36) NOT NULL COMMENT '关联玩家UUID',
    `inventory_type` TINYINT UNSIGNED NOT NULL COMMENT '0:背包, 1:末影箱',
    `slots_payload` MEDIUMBLOB NOT NULL COMMENT 'Protobuf压缩序列化的全槽位数据',
    `version` BIGINT UNSIGNED NOT NULL DEFAULT 1 COMMENT '乐观锁版本号',
    `updated_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_player_type` (`player_uuid`, `inventory_type`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='玩家背包与资产存储表';

-- 3. 资产与道具流转审计日志表 (金融级对账)
CREATE TABLE `asset_transactions` (
    `id` BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    `transaction_id` VARCHAR(64) NOT NULL COMMENT '全局唯一交易幂等流水号',
    `player_uuid` CHAR(36) NOT NULL COMMENT '操作玩家UUID',
    `change_type` VARCHAR(32) NOT NULL COMMENT '变动原因(MINE_REWARD/TRADE/PURCHASE)',
    `amount` BIGINT NOT NULL COMMENT '金币/资产变动值(可正可负)',
    `balance_after` BIGINT UNSIGNED NOT NULL COMMENT '变动后账户余额',
    `details` JSON DEFAULT NULL COMMENT '交易物品详情/元数据扩展',
    `created_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_tx_id` (`transaction_id`),
    KEY `idx_player_time` (`player_uuid`, `created_at`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='资产交易与防刷审计日志表';
```

## 四、 并发控制与数据一致性保障机制

### 4.1 Cache-Aside 缓存读写时序与更新策略

```
[玩家上线读流程]
  1. 查询 Redis: mcpe:player:inventory:{uuid}
  2. 若命中 (Cache Hit) -> 反序列化并返回
  3. 若未命中 (Cache Miss) ->
     a. 获取分布式互斥锁 (SETNX mcpe:lock:load:{uuid}, 3s)
     b. 从 MySQL 加载数据
     c. 回填写入 Redis (TTL 随机抖动: 7200s + rand(0, 600s))
     d. 释放分布式锁

[玩家下线/定时保存写流程]
  1. 玩家下线或定时 Checkpoint 触发
  2. 优先写入 MySQL (带事务保证与唯一流水号记录)
  3. 写入成功后，采用【延时双删】策略：
     a. 立即删除 Redis 缓存
     b. 延时 500ms 再次删除 Redis 缓存 (消灭主从同步延迟引发的脏缓存)
```

### 4.2 缓存穿透、击穿与雪崩防护规约

1. **防缓存穿透（Cache Penetration）**：
   - 对于查询不存在的恶意 UUID，在 Redis 存入空值（`{}`）并设置短暂的过期时间（$60$ 秒）。
   - 在微服务网关层部署 **布隆过滤器（Bloom Filter）**，拦截非法或未注册的 UUID 直接返回，严防攻击流量直穿 MySQL。
2. **防缓存击穿（Cache Breakdown）**：
   - 对超高频访问的全局热门资产或大服排行榜数据，采用 **互斥锁（Mutex Lock）** 重建策略：当缓存失效时，仅允许单个 Goroutine 获取分布式锁并访问数据库重构缓存，其余请求等待重试。
3. **防缓存雪崩（Cache Avalanche）**：
   - 严禁全量玩家缓存设置完全相同的过期时间。
   - 所有 Key 的过期时间引入 **随机抖动值（Jitter）**：$\text{TTL} = 7200\text{s} + \text{rand}(0, 600)\text{s}$，使大量缓存键的过期时间平滑分散在时间轴上。

### 4.3 道具复制与并发刷物品防御（防重防刷）
* **痛点**：在弱网或多端同时登录时，恶意玩家故意并发发送取回物品 RPC，若无并发控制会导致“一物多取”经典刷物品漏洞。
* **防御机制**：
  1. **基于 Redis 的原子分布式锁（SetNX + UUID）**：任何涉及物品存取的操作必须先加锁，持有锁后方可操作。
  2. **全局幂等交易序列号（Transaction ID）**：每个资产变更请求携带客户端生成的唯一 UUID，MySQL `asset_transactions` 表中建立唯一索引约束 `uk_tx_id`，底层数据库层面彻底物理拒绝重复扣减与充值。
  3. **乐观锁版本控制（Optimistic Locking）**：更新 `player_inventories` 时附加 `WHERE version = old_version` 条件，若版本号不匹配说明发生了并发竞争，立即回滚并重新加载。

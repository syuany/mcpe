# MCPE 工业级架构规范与防屎山工程守则 (Architecture Standards & Anti-Patterns)

> **修订历史**：2026-10-05 经由 Sprint 1/2 架构对齐与 Netty 零拷贝重构经验教训总结确立。  
> **适用范围**：MCPE 服务端全生命周期开发、PR 代码审查与后续 Sprint（世界、区块、实体、游戏循环等）实施。

---

## 1. 背景与历史教训复盘 (Root Cause Analysis)

在早期 Sprint 1~2 开发演进中，项目曾出现向“屎山代码”滑动的危险倾向：
1. **教程思维的致命缺陷**：
   * 为了“单文件能跑、尽快演示 Ping/Pong 或登录成功”，将网络 I/O、协议状态机、心跳定时器、路由分发全塞进 `TcpSession`；
   * 越权处理：让 `StatusHandler` 越权处理 `Handshake`，业务层到处充斥裸数字魔数（如 `0x00`, `0x23`, `100`, `"flat"`）。
2. **局部优化的权宜之计（造冗余轮子）**：
   * 在需要流式零拷贝切包时，没有在底层 `ByteBuffer` 原生实现引用计数与 COW，而是随手糊了一个 `ByteReader` 包装 `std::string_view`；
   * 后果：不仅引入悬挂指针与生命周期踩踏风险，还导致 `ByteReader` 100% 重复实现了 `ByteBuffer` 的所有数值反序列化方法，造成类泛滥和职责混乱。

为了杜绝此类“为了快速出结果而牺牲架构质量”的行为，确立以下不可逾越的工程法则。

## 2. 核心架构红线 (Non-Negotiable Architecture Rules)

### 红线一：四层单向解耦法则 (Strict Layering)

代码仓库严格划分为四大层次，依赖关系必须**单向向下**，绝对禁止逆向依赖或越层穿透：

```
┌────────────────────────────────────────────────────────┐
│ 4. Domain & Engine: World / Chunk / Entity / Inventory │  (纯游戏逻辑，不知网络为何物)
└───────────────────────────▲────────────────────────────┘
                            │ (调用领域服务 / 提交事件)
┌───────────────────────────┴────────────────────────────┐
│ 3. Protocol & Session: Handlers / ClientManager / MOTD  │  (协议编解码、会话状态机、身份校验)
└───────────────────────────▲────────────────────────────┘
                            │ (OnPacket 回调 / 发送队列)
┌───────────────────────────┴────────────────────────────┐
│ 2. Network Transport: TcpServer / TcpSession / Framing │  (Asio 异步 I/O、流式定界拆包)
└───────────────────────────▲────────────────────────────┘
                            │ (读写切片与内存管理)
┌───────────────────────────┴────────────────────────────┐
│ 1. Foundations: ByteBuffer (COW) / VarInt / ThreadPool  │  (纯无状态工具、高性能内存原语)
└────────────────────────────────────────────────────────┘
```

* **传输层（`network/`）禁令**：绝对禁止引入 Minecraft 协议业务概念（如 `Packet ID`、`GameProfile`、`NextState`）。
* **业务层（`world/`, `entity/`）禁令**：绝对禁止持有套接字 `socket` 或直接依赖网络层上下文。跨线程调用必须通过任务队列（如 `QueueTask`）异步派发。

### 红线二：单一职责与类膨胀约束 (Single Responsibility Principle)

* **一句话原则**：每个类、每个组件的职责必须能用一句话清晰阐述（如：`PacketFraming` 只管定界拆包，`TcpSession` 只管单个 TCP 连接生命周期与字节流收发）。
* **上帝类拦截**：一旦发现某个类的方法超过 15 个，或者同时承担“数据存储”、“业务逻辑”、“网络通信”中的两个以上角色，必须强制拆分。

### 红线三：严禁平行轮子，底层设施必须内聚 (No Duplicate Wheels)

* **杜绝临时 Wrapper**：当基础库无法满足高性能需求时（如切片零拷贝），必须**在原有核心类内部重构并夯实其底层存储模型**，严禁在旁边新建语义并列的借用类。
* **统一内存契约**：所有字节切片必须拥有清晰的生命周期所有权模型（如 `ByteBuffer` 的 `std::shared_ptr<Storage>` + Copy-On-Write 防护），从类型系统杜绝悬挂指针。

### 红线四：全面强类型化，彻底消灭魔数 (Zero Magic Numbers)

* **禁止裸字面量**：任何 Packet ID、协议状态、维度 ID、游戏模式、配置常量，必须集中定义在 `PacketTypes.h` / `GameTypes.h` 的 `enum class` 中。
* **业务强类型**：实体 ID、区块坐标、玩家 UUID 必须具有明确的强类型或结构体包装，禁止通篇裸 `int` 或裸 `string` 穿透。

## 3. 终态骨架设计法 (Production-Grade Skeleton First)

> **原则：哪怕当前 Sprint 只实现该模块 5% 的功能，骨架结构也必须直接对标 100% 工业级（Cuberite）标准构建。**

1. **拒绝“先写玩具再重构”**：
   * 严禁编写“仅供当前阶段演示的临时简化实现”。
   * 初始交付允许某些高级分支留白（抛出未实现异常或记录 Debug 日志），但组件边界、接口契约、类生命周期必须与终态完全一致。
2. **Cuberite 对齐自查**：
   * 编写任何核心系统前，必须先查阅 Cuberite 对应模块（如 `cWorld`, `cChunk`, `cProtocol`）的设计思路，吸取其经验，避免重复踩坑。

---

## 4. 机械化质量门禁 (Definition of Done - DoD)

任何新功能或重构提交合并前，必须满足以下 4 项硬性指标：

1. **编译零告警**：
   * 开启 `-Wall -Wextra -Wpedantic`，编译过程保持 0 Errors, 0 Warnings。
2. **动态内存安全（ASan + UBSan）**：
   * 运行测试与集成验证脚本时，AddressSanitizer / UndefinedBehaviorSanitizer 必须零泄漏、零越界、零未定义行为。
3. **负向契约与边界测试**：
   * 单元测试不仅要覆盖 Happy Path，还必须覆盖：半包等待零副作用、恶意超长畸形包防御、并发切片隔离性验证。
4. **端到端协议闭环**：
   * 必须通过真实客户端或自动化脚本（如 `test_ping.py`, `test_login.py`）的全链路回归测试，服务端日志无异常报错。

---

## 5. 后续 Sprint（Sprint 3+）实施标准流程 (RFC 机制)

进入 Sprint 3（区块与世界系统）时，必须按以下三步推进：
1. **RFC 设计先行**：明确 `World`、`Chunk`、`ChunkSection` 的内存拓扑与并发归属，形成设计共识；
2. **底层序列化对齐**：使用已完备的 Netty 零拷贝 `ByteBuffer` 构建 `ChunkDataPacket`；
3. **增量交付与 DoD 验收**：分批接入，每步保持测试全绿与零代码异味。
